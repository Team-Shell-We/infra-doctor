> 마지막 갱신 기준: `develop` (PR #45 언어 전환 전체 커버리지, #46 explain 미도입 topic 명확화, #49 visualize, #50/#51 generate, #53 recommend 문구 정리, #54 recommend 복잡도 신호 확장, #55 Next Step 레이어, #56 doctor CI 게이트, #64 Maven 지원, #66 update release API, #67 Gradle Kotlin DSL 감지 수정, #70 Maven 인프라 감지 누락 수정, #77 help/타임아웃/recommend 라벨/visualize DB 노드 정리, #81 스캐폴드/죽은 코드 정리, #82 v0.2.0 릴리스, #84 중복 로직 통합, #85 주석 스타일 통일, #79 CONTRIBUTING 분리)

## 프로젝트 설명

AI 기반 프로젝트 운영 진단 및 인프라 구축 가이드 CLI. Spring Boot 프로젝트를 분석하여 현재 운영 구조를 시각화하고, 운영 환경에서 부족한 요소를 진단하며, Docker/Kubernetes/CICD 등의 설정 파일과 개선 가이드를 자동 생성하는 오픈소스 CLI.

## Pain Point

- 백엔드 개발자는 애플리케이션 개발은 가능하지만 운영 환경을 구성하는 과정에서 많은 어려움을 겪음 (Docker는 언제 쓰는지, Nginx는 어디 위치하는지, Redis는 왜 필요한지, Kubernetes는 언제 도입해야 하는지 등)
- 인터넷에 정보는 많지만 내 프로젝트 기준으로 알고 싶으면 코드를 통째로 AI에게 복붙해 질문해야 하는 공수가 큼
- Infra Doctor는 프로젝트를 분석해 운영 관점에서 현재 구조를 이해시키고, 개선 방향과 실제 적용 가능한 설정 파일을 함께 제공하는 것을 목표로 함

## 핵심 설계 원칙 (구현 중 확립됨)

원래 명세엔 없던 내용이지만, `explain`/`doctor`를 구현하면서 실측으로 확인하고 이후 모든 AI 명령어에 적용한 원칙입니다.

> **AI는 사실을 판단하지 않고, 코드가 이미 결정한 사실을 설명만 한다.**

- `doctor`는 애초에 AI를 아예 쓰지 않고 100% 규칙 기반(YAML 룰)으로 구현했습니다 (아래 개별 항목에서 명세와의 차이로 다시 언급).
- `explain`은 처음엔 "Current Status"(관련 파일 존재 여부)까지 AI에게 자유롭게 생성시켰는데, 스캔한 적도 없는 파일명(`Dockerfile.dev` 등)을 그럴듯하게 지어내는 걸 실측으로 확인했습니다. 이후 "사실 판단"(무엇이 있는지)은 전부 `project.Info` 기반 Go 코드가 결정하고, AI는 "왜 중요한지" 설명(자연어)만 담당하도록 구조를 바꿨습니다.
- `recommend`도 같은 원칙을 처음부터 적용 — 배포 전략(Docker Compose vs Kubernetes) 추천 자체는 코드가 결정론적으로 판단하고, AI는 그 이유(Reason)만 문장으로 풀어씁니다.
- 이 원칙 덕분에 AI 명령어들은 재현성 있는 핵심 정보(체크리스트, 추천값, Next Step 등)를 갖고, AI는 "설명을 자연스럽게 해주는 역할"로 범위가 명확해졌습니다.

## 사용 시나리오

신규 Spring Boot 프로젝트에 처음 도입할 때 명령어를 사용하는 순서 예시입니다. 각 명령어의 상세 명세는 아래 "명령어별 상세 명세" 참고.

```bash
cd my-project

infra-doctor init                  # .infra-doctor/config.yaml 생성 (generate 커스터마이징용, 없어도 동작함)
infra-doctor scan                  # 뭐가 감지됐는지 먼저 확인
infra-doctor doctor                 # 준비도 점수 + 부족한 항목 확인
infra-doctor login                  # explain/recommend 쓰려면 최초 1회 필요

infra-doctor recommend              # Docker Compose vs Kubernetes 추천 + 이유
infra-doctor explain docker         # 왜 필요한지 프로젝트 맥락으로 설명

infra-doctor generate compose       # recommend가 안내한 target으로 실제 파일 생성
infra-doctor doctor                 # 점수가 올랐는지 재확인

infra-doctor visualize architecture # 완성된 인프라 구조를 다이어그램으로 확인
```

CI 파이프라인에서는 `doctor --fail-under <score>`로 인프라 회귀를 게이트할 수 있습니다 (이슈 #42, 아래 doctor 항목 참고).

위 명령어를 하나씩 실행하는 대신 `infra-doctor export`로 리포트+다이어그램+생성 파일을 `infra-doctor/` 디렉터리 하나에 한 번에 모을 수도 있습니다(이슈 #39, 아래 export 항목 참고).

`.infra-doctor/config.yaml`을 만들지 않고 바로 `generate`를 실행해도 동작합니다 — 이 경우 포트/서비스명/이미지 등은 스캔 결과 기반 기본값을 쓰고, 생성 파일은 프로젝트 루트에 바로 써집니다. `init`으로 만든 기본 config는 `output.directory: .infra-doctor/generated`를 지정하므로, `init` 이후엔 생성 파일이 루트가 아니라 그 하위 디렉터리에 써진다는 차이가 있습니다.

### scan

| 항목 | 내용 |
|---|---|
| 명령어 | `infra-doctor scan [path]` |
| 구현 상태 | ✅ 완료 (MVP) |
| AI 사용 여부 | N |
| 담당자 | gimye |

**기능 설명**: 프로젝트를 분석하여 현재 사용 중인 기술 스택과 인프라 구성 요소를 감지합니다. `path`를 생략하면 현재 디렉터리를 분석합니다.

**분석 대상**: Spring Boot 버전 / Gradle·Maven / Java 버전, Spring Security·JPA·Kafka·AWS SDK·Lombok·Actuator·OpenAPI 의존성, PostgreSQL·MySQL·MariaDB·Redis, Docker·Docker Compose·Kubernetes, GitHub Actions(트리거/브랜치/Job까지), 프로파일(dev/prod/test/default).

**출력 예시**
```
🔍 Project Scan

 Framework
   ✓ Spring Boot 3.5.7
   ✓ Gradle
   ✓ Java 17

 Dependencies
   ✓ Spring Security
   ✓ Spring Data JPA
   ...

 Database
   ✓ PostgreSQL
   ✓ Redis

 Infrastructure
   ✓ Docker
      └─ Dockerfile
   ✗ Docker Compose
   ✗ Kubernetes

 CI/CD
   ✗ GitHub Actions

 Profiles
   ✓ dev
      └─ application-dev.yml
   ...
```

빌드 파일(`build.gradle`/`pom.xml`) 탐색은 지정한 `path` 디렉터리에서만 이뤄지고, Docker/Compose/K8s/GitHub Actions/Profile 파일 탐색은 하위 디렉터리를 재귀로 훑되 `.git`/`.gradle`/`.idea`/`build`/`node_modules`/`target`/`.infra-doctor`는 제외합니다(`internal/analyzer/walk.go`). Gradle/Maven 둘 다 동일하게 적용됩니다(PR #70) — 단, 의존성/DB/프레임워크 감지 자체는 두 빌드 도구 모두 루트 빌드 파일 하나만 읽으므로, 실제 의존성이 자식 모듈에 선언된 멀티모듈 프로젝트에선 놓칠 수 있습니다(아래 "수정해야 하는 사항" 참고).

### doctor

| 항목 | 내용 |
|---|---|
| 명령어 | `infra-doctor doctor [path] [--json] [--fail-under <score>]` |
| 구현 상태 | ✅ 완료 |
| AI 사용 여부 | **N (원래 명세는 Y였으나 구현 시 100% 규칙 기반으로 전환)** |
| 담당자 | gimye |

**기능 설명**: 프로젝트의 이슈 준비도(Deployment Readiness)를 0~100% 점수로 진단합니다. 진단 룰은 세 카테고리로 나뉘며, 전부 `internal/doctor/rules/*.yaml`로 관리되고 자동 스키마 검증(테스트+CI)을 거칩니다.

**CI 게이트(이슈 #42)**: `--json`은 박스 UI 대신 `doctor.Result`를 JSON으로 출력(사람이 보는 기본 출력은 플래그 없을 때 그대로 유지). `--fail-under <score>`는 점수가 기준 미만이면 `os.Exit(1)` — 플래그를 안 주면 기존처럼 항상 exit 0. 두 플래그는 독립적이라 같이 써도, 따로 써도 됨.

- **deployment**: Docker/GitHub Actions 조합 (`no_deployment` -40 Critical, `no_docker` -20 Warning, `no_github_actions` -15 Warning)
- **production**: 운영 하드닝 (`no_health_check`/`no_reverse_proxy`/`no_monitoring` 각 -10~-15 Warning, `no_log_rotation` -5 Info, `no_backup` -20 Critical)
- **localdev**: 로컬 개발 편의성 (`no_compose_with_dependencies` -10 Warning, `no_dev_profile` -5 Info)

**Infrastructure Check 체크리스트(7항목, 결정론적)**: Docker, Docker Compose, Health Check, Reverse Proxy, Monitoring, Log Rotation, DB Backup

**출력 예시**
```
🩺 Infrastructure Doctor

Deployment Readiness
 ████░░░░░░░░░░░░░░░░░░░░░░░░░░ 15%

Infrastructure Check
 ✓ Docker
 ✗ Docker Compose
 ✗ Health Check
 ✗ Reverse Proxy
 ✗ Monitoring
 ✗ Log Rotation
 ✗ DB Backup

Recommendation
 • Configure GitHub Actions.
 • Add a docker-compose.yml that starts local database/Redis dependencies with one command.
 ...
```

**기여 가이드**: `internal/doctor/rules/README.md`에 룰 작성 규칙(id 네이밍, category/level enum, score 범위, PR 체크리스트)이 정리되어 있습니다.

### login

| 항목 | 내용 |
|---|---|
| 명령어 | `infra-doctor login` |
| 구현 상태 | ✅ 완료 |
| AI 사용 여부 | N (다른 AI 명령어의 전제조건) |
| 담당자 | gimye |

**기능 설명**: AI 명령어(`explain`, `recommend`) 사용을 위한 로그인. 방법을 선택합니다.

1. **OpenAI API Key** — ✅ 구현됨. 마스킹 입력(`golang.org/x/term`), OpenAI API로 실제 키 검증 후 `~/.infra-doctor/config.json`에 저장(`{"provider":"openai","apiKey":"...","login":true}`, 파일 권한 `0600`/디렉터리 `0700`).
2. **Infra Doctor Account** — ❌ 백엔드 없음. 메뉴에서 선택은 되지만 "아직 지원하지 않습니다" 안내만 출력.

**주의**: 여기서 저장하는 `~/.infra-doctor/config.json`(홈 디렉터리, AI 자격증명 + CLI 전역 설정)은 `init` 명령어가 프로젝트 디렉터리에 만드는 `.infra-doctor/config.yaml`(분석 설정)과 전혀 다른 파일입니다.

**출력 예시**
```
🔐 Login

Select Login Method
  1. OpenAI API Key
  2. Infra Doctor Account
Choose (1-2): 1

OpenAI API Key
> ********

✅ OpenAI API Key verified.
✅ Login completed.

Provider
OpenAI
```

### explain <topic>

| 항목 | 내용 |
|---|---|
| 명령어 | `infra-doctor explain <topic> [path]` |
| 구현 상태 | ✅ 완료 |
| AI 사용 여부 | Y (일부 섹션만) |
| argument | compose, container, docker, github-actions, image, k8s, nginx, postgres, rds, redis |
| 담당자 | gimye |

**기능 설명**: 지정한 기술이 **현재 스캔된 프로젝트 맥락에서** 어떤 역할을 하는지 설명합니다. `login` 필요.

**섹션별 생성 방식**:
| 섹션 | 생성 주체 |
|---|---|
| Current Project | AI (스캔 요약 기반, 고정 프롬프트) |
| Build Flow | AI |
| Why \<Topic\>? | AI |
| Current Status | **코드(결정론적)** — topic별로 어떤 파일/설정을 확인할지 하드코딩된 매핑(`internal/ai/explain/status.go`)으로 판단, AI는 관여하지 않음 |

아직 프로젝트에 없는 topic(예: k8s 없는데 `explain k8s`)을 설명할 때는 "현재 상태"를 AI 서술보다 먼저 보여주고, 코드가 결정한 미도입 안내 배너를 상단에 표시합니다(`explain.TopicPresent`). AI 프롬프트에도 absent로 표시된 사실은 가정법으로 서술하라는 지시가 들어가 있습니다.

**출력 예시**
```
💡 Docker Explained

Current Project
 ✓ Uses Spring Boot 3.5.7 with Gradle, leveraging Java 17.
 ✓ Relies on PostgreSQL and Redis for data management.
 ...

Build Flow
 Dockerfile defines the build instructions for the application.
 ...

Why Docker?
 • Docker ensures consistent environment setups across development,
   testing, and production.
 ...

Current Status
 ✓ Dockerfile
 ✗ Docker Compose
 ✗ Health Check
```

**로그인 안 된 경우**: `You're not logged in. Run 'infra-doctor login' to set up your OpenAI API Key first.` 출력 후 종료.

### recommend

| 항목 | 내용 |
|---|---|
| 명령어 | `infra-doctor recommend [path]` |
| 구현 상태 | ✅ 완료 |
| AI 사용 여부 | Y (일부 섹션만) |
| 담당자 | gimye |

**기능 설명**: 프로젝트에서 감지된 인프라 복잡도 신호(Kafka/관계형DB/Redis/다중 CI워크플로 개수)를 기반으로 배포 전략(Docker Compose vs Kubernetes)을 추천합니다. `login` 필요.

이전엔 "프로젝트 규모를 분석"이라고 설명했으나, 실제로는 트래픽/팀 규모/마이크로서비스 개수 같은 진짜 "규모" 지표를 볼 방법이 없습니다(리포 하나만 스캔). 스캔 가능한 정적 신호 카운팅이 정확한 동작이라 문구를 그에 맞게 정리했습니다(이슈 #44).

**신호 6개(이슈 #52로 확장, `complexityThreshold = 4`)**: Kafka 사용, 관계형 DB 사용, Redis 사용, CI 워크플로 2개 이상, API 엔드포인트 20개 초과(`internal/analyzer/api.go`가 `.java` 소스에서 `@RestController`/`@GetMapping` 등 어노테이션 카운팅), 멀티모듈 구조(Gradle은 `internal/analyzer/modules.go`가 `settings.gradle`의 `include` 개수를, Maven은 `AnalyzeMavenModules`가 `pom.xml`의 `<modules>` 개수를 카운팅 — PR #70). 이미 Kubernetes를 쓰는 프로젝트는 이 신호들과 무관하게 즉시 유지되지만, replicas가 2 이상이면 "이미 스케일 중"이라는 근거가 Reason에 추가됩니다(`internal/analyzer/infrastructure.go`가 manifest의 `replicas:` 값도 파싱).

**섹션별 생성 방식**:
| 섹션 | 생성 주체 |
|---|---|
| Current Stack | 코드 (`ai.Summary` 재사용) |
| Recommended | **코드** — 이미 K8s 매니페스트가 있으면 Kubernetes 유지, 아니면 복잡도 신호(Kafka/DB/Redis/다중 CI워크플로) 개수로 Kubernetes vs Docker Compose 판단 |
| Kubernetes 적합 여부 | 코드 |
| Reason | AI — 코드가 결정한 추천 이유(라벨)를 자연어로 풀어씀. **추천 자체를 바꾸지 못하도록 시스템 프롬프트로 강제** |
| Next Step | 코드 — 부족한 설정(compose/k8s manifest/CI)에 따라 `infra-doctor generate ...` 명령어 제안 |

**출력 예시**
```
🚀 Deployment Recommendation

Current Stack
 ✓ Spring Boot 3.5.7 (Gradle), Java 17
 ✓ PostgreSQL
 ✓ Redis

Recommended
 ⭐ Docker Compose

Kubernetes
 ✗ Not Recommended

Reason
 • Your project utilizes a single Spring Boot API server, making
   Docker Compose an ideal fit...
 ...

Next Step
 infra-doctor generate docker
 infra-doctor generate ci
```

| 구현 상태 | ✅ 완료 (PR #50/#51, 이슈 #37) |
| AI 사용 여부 | N |
| argument | docker, compose, nginx, k8s, ci, architecture(=필요한 것 전부 한 번에) |
| Output | Dockerfile, docker-compose.yml, nginx.conf, GitHub Actions Workflow, Kubernetes Manifest(deployment/service/configmap) |
| 담당자 | jade & gimye |

**기능 설명**: 프로젝트 분석 + `doctor` 진단 결과를 기반으로 설정 파일을 프로젝트 루트에 생성합니다(`internal/generate`, `Generator` 인터페이스 + `Registry` 패턴, `.tmpl` + `go:embed`). `.infra-doctor/config.yaml`의 `output`/`generate` 설정을 실제로 읽어 포트/서비스명/이미지/네임스페이스 등을 커스터마이징할 수 있습니다. 이미 파일이 있으면 `--force` 없이는 거부, `--dry-run`으로 미리보기 가능. `recommend`의 Next Step이 이 명령어를 안내합니다.

`architecture` target은 `visualize architecture`(다이어그램)와 다른 의미로, `doctor` 진단 결과 부족한 것(docker/compose/nginx/ci)만 골라 한 번에 생성합니다.

생성 파일은 `internal/analyzer`가 인식하는 정확한 파일명/내용으로 나와서, 생성 직후 `doctor`/`scan`이 바로 "있음"으로 인식합니다(`Dockerfile`엔 `HEALTHCHECK`, `docker-compose.yml`엔 DB별 필수 환경변수+`healthcheck`+`depends_on: condition: service_healthy`, k8s manifest엔 `resources` requests/limits, CI엔 의존성 캐싱+최소 `permissions`). 모든 생성 파일에 "다음 할 일" 안내 배너가 `config --lang`(en/ko)을 따라 포함됩니다.

### 아직 남은 것 (우선순위순)

1. **`update`의 버전 파서가 pseudo-version을 못 견딤** — `go install ...@브랜치`처럼 정확한 태그가 아닌 방식으로 설치하면 나오는 Go pseudo-version이나 pre-release 태그를 만나면 하드 실패함. `(devel)`/`unknown`처럼 "dev"로 우아하게 폴백하는 케이스에 포함시켜야 함.
2. **의존성/DB 감지가 루트 빌드 파일만 읽음** — Gradle·Maven 둘 다 자식 모듈까지 안 들어감. 실제 의존성이 자식 모듈에 있는 멀티모듈 프로젝트에선 JPA/Kafka/DB 감지를 놓칠 수 있음. 두 빌드 도구 모두 대칭적으로 갖고 있는 원래부터의 한계.
3. **GitHub Actions 축약형 트리거(`on: push`, `on: [push, pull_request]`)가 0개로 파싱됨** — 여러 줄 매핑 형태만 지원. 에러 없이 조용히 빈 값.
4. **`config`가 바꿀 수 없는 설정을 바꿀 수 있는 것처럼 보여줌** — "Output Format"/"Auto Export"를 표시하는데 해당 플래그가 아예 없어서 절대 안 바뀜. `--lang`만 실제로 동작.
5. **`donate`에 "Buy Me a Coffee" 링크 누락** — 명세엔 있으나 구현에서 빠짐. (우선순위 낮음, 보류 중)
6. **`doctor`의 룰 YAML 번역 미지원** — 이중 언어 YAML 필드 설계가 필요한 별도 작업.
7. **`ui.Wrap`이 박스보다 긴 단어 하나를 강제로 안 끊음** — AI가 생성한 텍스트에 긴 URL 같은 게 섞이면 박스 테두리 정렬이 깨질 수 있음.
8. **테스트 커버리지 공백** — `cmd/*.go` 대부분(doctor·generate만 테스트 있음), `internal/utils`, `internal/ai/openai`에 전용 테스트가 없음.
